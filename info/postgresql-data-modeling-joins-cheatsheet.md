# PostgreSQL — Нормализация, денормализация и JOIN

## 1. Нормализация: разделяем факты по смыслу

Нормализация уменьшает избыточность и аномалии изменения данных: один
и тот же факт не приходится исправлять во множестве строк.

Пример модели:

- `users(id, name)` — пользователь.
- `orders(id, user_id, status)` — заказ, ссылка на пользователя.
- `order_items(id, order_id, product_id, quantity, unit_price)` — позиции заказа.

Текущее имя пользователя хранится в `users`, а не копируется в каждый заказ.
Связи закрепляются внешними ключами; обязательность и уникальность —
соответствующими ограничениями.

Кратко о нормальных формах:

| Форма | Практический ориентир |
|---|---|
| 1NF | Нет повторяющихся групп вроде `product_1`, `product_2`; позиции представлены строками |
| 2NF | Неключевые атрибуты зависят от всего кандидатного ключа, а не от его части |
| 3NF | Нет транзитивной зависимости неключевых атрибутов от ключа через другие неключевые атрибуты |

Это краткие ориентиры, не полные формальные определения.

**Когда применять:** данные часто изменяются, важны целостность,
отсутствие противоречий и независимое развитие сущностей.
Для обычной прикладной БД это разумная отправная точка.
Не нужно выносить каждое поле в отдельную таблицу.

## 2. Денормализация: сохраняем данные для конкретного чтения

Денормализация осознанно добавляет копии или производные данные:
например, `orders.items_total` либо таблицу дневных итогов.

| Ситуация | Подход |
|---|---|
| Обычный CRUD, запросы укладываются в требования | Сохранять нормализованную модель |
| Частый дорогой отчёт после проверки запросов и индексов | Рассмотреть агрегатную таблицу или materialized view |
| Нужен быстрый доступ к вычисляемому значению | Хранить результат с понятным механизмом обновления |
| Не определены допустимая задержка и способ синхронизации | Сначала определить их, затем денормализовать |

Для каждого сохранённого результата определите:
**источник истины → кто обновляет → допустимое отставание → как пересчитать**.
Синхронное обновление можно объединить с изменением исходных данных
в транзакцию; асинхронное требует обработки задержек и повторов.

Обычный `VIEW` хранит запрос, а `MATERIALIZED VIEW` — его результат,
который нужно обновлять через `REFRESH`.

**Исторический снимок — отдельный факт.** Цена покупки
`order_items.unit_price` не обязана совпадать с текущей ценой товара.
Её нельзя автоматически «синхронизировать» при изменении каталога.

## 3. Какой JOIN выбирать

Выбирайте JOIN по требуемому результату, а не по предполагаемой скорости.

| Тип | Что возвращает | Когда применять |
|---|---|---|
| `INNER JOIN` | Только совпавшие пары | Заказы вместе с существующими пользователями |
| `LEFT JOIN` | Все строки слева и совпадения справа; иначе справа `NULL` | Все пользователи, включая пользователей без заказов |
| `RIGHT JOIN` | Все строки справа и совпадения слева | Зеркальный вариант LEFT; часто понятнее переставить таблицы |
| `FULL OUTER JOIN` | Совпадения и несовпавшие строки обеих сторон | Сверка двух наборов |
| `CROSS JOIN` | Все комбинации: N × M строк | Матрица «товар × регион» |
| Self join | Таблица соединяется сама с собой через разные aliases | Сотрудник и его руководитель; это способ применения JOIN, не отдельный тип |

### INNER JOIN: заказы с именами пользователей

```sql
SELECT o.id, u.name
FROM orders AS o
JOIN users AS u ON u.id = o.user_id;
```

### LEFT JOIN: все пользователи и их оплаченные заказы

```sql
SELECT u.id, o.id AS order_id
FROM users AS u
LEFT JOIN orders AS o
    ON o.user_id = u.id
   AND o.status = 'paid';
```

Здесь фильтр статуса в `ON` сохраняет пользователей без оплаченных
заказов. Перенос `o.status = 'paid'` в `WHERE` исключит их.

### EXISTS: нужны пользователи с заказами, а не сами заказы

```sql
SELECT u.id
FROM users AS u
WHERE EXISTS (
    SELECT 1 FROM orders AS o WHERE o.user_id = u.id
);
```

`EXISTS` не размножает пользователя по количеству заказов.
Для пользователей без заказов используйте `NOT EXISTS`.

## 4. Типичные ошибки

- **Размножение строк.** Один заказ с тремя позициями после JOIN даст
  три строки. Если добавить две оплаты, можно получить шесть.
  Перед суммированием агрегируйте независимые дочерние наборы
  отдельно до нужного уровня — например, одна строка на заказ.
- **DISTINCT скрывает причину.** Он не исправляет уже завышенную сумму.
- **COUNT после LEFT JOIN.** `COUNT(*)` считает и строку без совпадения;
  для числа заказов используйте `COUNT(o.id)`, если `id` не допускает NULL.
- **NULL не сравнивается через `= NULL`.** Используйте `IS NULL`.
  Для проверки отсутствия связей часто понятнее `NOT EXISTS`,
  чем `NOT IN`, чувствительный к NULL.
- **NATURAL JOIN зависит от названий колонок.** Предпочитайте явный
  `ON` или `USING`, чтобы добавление одноимённой колонки не изменило связь.

## 5. Что делать, если JOIN медленный

Сначала проверьте условия соединения, число строк, статистику,
индексы и реальный план. Большое число таблиц само по себе
не является основанием для денормализации.

`Nested Loop`, `Hash Join`, `Merge Join` — алгоритмы выполнения,
а `INNER`/`LEFT`/`FULL` — смысл результата. Алгоритм выбирает планировщик;
универсально лучшего нет.

См. также: [индексы и EXPLAIN](postgresql-indexes-cheatsheet.md#9-как-проверить-индекс-через-explain),
[транзакции](postgresql-transactions-cheatsheet.md).
