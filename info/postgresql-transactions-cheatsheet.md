# PostgreSQL Transactions — Cheatsheet

## 1. Что гарантирует транзакция

**Транзакция** объединяет связанные операции с данными: они фиксируются вместе либо откатываются.

| Свойство ACID | Практический смысл |
|---|---|
| Atomicity | Частично выполненная операция не должна остаться в БД |
| Consistency | Ограничения БД и корректная логика приложения сохраняют инварианты данных |
| Isolation | Правила видимости и взаимодействия конкурентных транзакций зависят от уровня изоляции |
| Durability | Зафиксированные изменения сохраняются после сбоя; гарантии зависят от настроек надёжности |

**Атомарность не устраняет гонки:** два клиента могут прочитать одинаковые данные и принять конфликтующие решения. Выбор изоляции и защиты от конкуренции — в [шпаргалке по блокировкам](postgresql-locks-cheatsheet.md#3-mvcc-и-уровни-изоляции).

## 2. Границы: BEGIN / COMMIT / ROLLBACK

- Без явного transaction block каждый отдельный statement выполняется в транзакции; при обычном autocommit успешный statement фиксируется автоматически. Драйвер может управлять этими границами сам.
- `BEGIN` начинает явную транзакцию.
- `COMMIT` фиксирует изменения; ошибка может возникнуть и на этом этапе, например при отложенной проверке ограничения.
- `ROLLBACK` отменяет изменения текущей транзакции.

### Пример: заказ и его позиции

Предполагаются существующие таблицы `orders` и `order_items`; `orders.id` генерируется БД.

```sql
BEGIN;

WITH new_order AS (
    INSERT INTO orders (user_id, status)
    VALUES (10, 'draft')
    RETURNING id
)
INSERT INTO order_items (order_id, product_id, quantity)
SELECT new_order.id, item.product_id, item.quantity
FROM new_order
CROSS JOIN (VALUES (101, 2), (102, 1)) AS item(product_id, quantity);

COMMIT;
```

При ошибке приложение выполняет `ROLLBACK`: заказ без позиций не сохраняется. Здесь обе вставки уже объединены в один атомарный statement; явный `BEGIN` нужен, если к операции добавляются другие связанные запросы.

## 3. Ошибки и SAVEPOINT

После SQL-ошибки внутри явной транзакции обычные запросы отклоняются с `25P02` (`in_failed_sql_transaction`). Выполните `ROLLBACK` либо откатитесь к savepoint, созданному **до ошибки**.

```sql
BEGIN;
UPDATE orders SET status = 'confirmed' WHERE id = 42;

SAVEPOINT optional_step;
UPDATE orders SET note = 'temporary note' WHERE id = 42;
ROLLBACK TO SAVEPOINT optional_step; -- отменили только изменение note
RELEASE SAVEPOINT optional_step;

COMMIT; -- изменение status сохраняется
```

В этом примере предполагается колонка `orders.note`. Если необязательный шаг завершился SQL-ошибкой, приложение также может выполнить `ROLLBACK TO SAVEPOINT optional_step` и продолжить, если это допустимо по смыслу операции.

`SAVEPOINT` — частичный откат, **не независимая вложенная транзакция**. `RELEASE` не фиксирует изменения: внешний `ROLLBACK` отменит их тоже. Ошибки сериализации и deadlock обрабатывайте по [правилам retry всей транзакции](postgresql-locks-cheatsheet.md#10-deadlocks-ожидания-и-retry).

## 4. Работа из приложения

1. Получите соединение из пула и используйте его для всех запросов от `BEGIN` до `COMMIT`/`ROLLBACK`.
2. Если ORM предоставляет transaction callback, выполняйте запросы через переданный `tx`, включая вызовы вложенных функций.
3. Дождитесь завершения всех запросов и `COMMIT`, прежде чем сообщать об успехе.
4. При ошибке откатите транзакцию и передайте ошибку вызывающему коду. Освобождайте соединение в `finally`; неисправное соединение исключайте из пула по правилам драйвера.

**Ноль изменённых строк — не SQL-ошибка.** Проверяйте `RETURNING`/число строк; если обязательная операция не выполнена, приложение должно само прервать транзакцию.

## 5. Внешние эффекты и пределы rollback

- HTTP-запрос, письмо или публикация сообщения не откатываются вместе с изменениями БД. Успешный внешний вызов не означает, что последующий `COMMIT` пройдёт.
- Отправка сразу после `COMMIT` тоже оставляет окно сбоя: данные уже сохранены, а сообщение ещё не отправлено.
- Если доставка обязательна, применяйте **outbox**: сохраняйте событие в таблицу вместе с данными, затем отдельный worker отправляет его с повторами. Получатель должен обрабатывать дубли идемпотентно.
- Значения sequence (`serial`/`identity`) после rollback не возвращаются: пропуски в ID нормальны.

## 6. Типичные ошибки

| Ошибка | Как избежать |
|---|---|
| Забытый `COMMIT`/`ROLLBACK` | Явные границы и гарантированное завершение транзакции |
| Ошибка перехвачена и скрыта | Передавать её наружу; частичное продолжение делать только осознанно через savepoint |
| Запрос выполнен через общий pool/ORM вместо `tx` | Передавать транзакционное соединение во все участвующие функции |
| Ожидание HTTP или действий пользователя внутри транзакции | Держать транзакцию короткой; внешние эффекты координировать отдельно |
